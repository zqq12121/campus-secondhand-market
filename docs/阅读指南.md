# 阅读指南

这份文档帮你从零读懂这个项目：先看整体结构，再按推荐顺序读代码，最后跟着几条关键流程把各模块串起来。接口细节以 [接口文档](接口文档.md) 为准，本文只讲「代码在哪、为什么这样组织」。

下文的 `campustrade/` 指 `backend/src/main/java/com/campustrade/`。

---

## 1. 整体结构

```text
浏览器 ──► Nginx（前端静态资源 /、/admin/）
              │ /api、/ws、/uploads               │ /api/v1/ai
              ▼                                   ▼
        Java 后端 :8080  ◄──── 带用户 token 调用 ──── ai-service :8090（Python）
              │                                    │
   MySQL ─ Redis ─ RabbitMQ ─ ES（可选）        MySQL 只读 + Redis
```

| 目录 | 是什么 | 从哪读起 |
| --- | --- | --- |
| `backend/` | Spring Boot 单体，所有业务都在这里 | 本文第 2～5 节 |
| `frontend/` | Vue 3：用户端 `src/web`、后台 `src/admin`、共享 `src/shared`，`mock/` 是内存版后端 | 第 7 节 |
| `ai-service/` | Python FastAPI + LangGraph 的 AI 助手 | 第 8 节 |
| `sql/` | `schema.sql` 表结构（带注释，读业务前先扫一遍）、初始数据、升级脚本 | — |
| `prototype/` | 静态 HTML 原型，界面以它为准 | — |
| `docs/` | 接口文档、本文 | — |

**为什么是单体而不是微服务**：后端约 1.2 万行，下单、扣库存、放款、加信用分都要在同一个数据库事务里完成。拆成微服务就得引入分布式事务、注册中心、网关、链路追踪，基础设施会比业务代码还多。这里用的是「模块化单体」：一个进程，内部按业务分模块，模块之间只通过 Service 调用。Java 后端和 Python AI 服务分开，是因为语言和运行时不同，这才是值得拆服务的理由。


### 一个业务模块长什么样

以订单为例，每个模块都遵循同样的结构：

```text
module/order/
├── OrderController       HTTP 入口：参数校验、取当前用户，然后调 Service
├── OrderService          业务逻辑
├── OrderDtos             请求 / 响应对象（record）
├── OrderStateMachine     模块内的领域规则（不是每个模块都有）
├── OrderTimeoutJob       本模块的定时任务（@Scheduled），文件名以 Job 结尾
├── entity/               表对应的实体：TradeOrder、OrderLog
└── mapper/               MyBatis-Plus Mapper：TradeOrderMapper、OrderLogMapper
```

规则只有三条：

1. **表归模块**：每张表的实体和 Mapper 放在「主要负责写它」的模块里，例如 `trade_order` 在 `order`，`balance_log` 在 `user`。
2. **跨模块调 Service**：别的模块需要数据时，优先调对方的 Service；只读查询直接用对方的 Mapper 也可以（看板、后台列表就是这样）。
3. **后台按域分包**：后台的同一类功能放在同一个子包，例如 `admin/goods` 里是商品审核和商品管理。

## 3. 一个请求是怎么走完的

以 `GET /api/v1/orders/6001` 为例：

1. `common/TraceIdFilter`：生成 traceId，写进日志 MDC 和响应体，排查问题时按它搜日志。
2. `security/JwtAuthFilter`：解析 `Authorization: Bearer ...`，校验签名、黑名单和失效时间点，把当前用户放进 SecurityContext。
3. `config/SecurityConfig`：按路径判断要不要登录、要哪个角色；后台接口在方法上再用 `@PreAuthorize` 校验权限码。
4. `OrderController`：用 `CurrentUser.id()` 取当前用户，调 `OrderService.detail`。
5. `OrderService`：做权限和业务判断，失败就 `Biz.check(...)` 抛 `BizException`。
6. `TradeOrderMapper`：MyBatis-Plus 查库。
7. 成功时返回 `R.ok(data)`；抛异常时由 `common/GlobalExceptionHandler` 统一转成 `{code, message, data}`。

看懂这 7 步，其他接口都是同一个套路。

## 4. 推荐阅读顺序

| 步骤 | 读什么 | 学到什么 |
| --- | --- | --- |
| 1 | `sql/schema.sql`、`common/Consts`、`common/ErrorCode` | 有哪些表和状态，错误码怎么定义 |
| 2 | `module/common` 全部 | 最简单的模块：Controller → Service → Mapper |
| 3 | `security/` + `module/auth` | JWT 登录、token 黑名单、登录失败限流和锁定 |
| 4 | `module/goods`：`GoodsService.create` → `GoodsAuditService.submit` | 发布、自动审核、审核通过后触发求购匹配和关注通知 |
| 5 | `module/order`：`OrderStateMachine` → `OrderService.create` → `OrderFlow` | 状态机、乐观锁、幂等、事务提交后再发消息 |
| 6 | `module/pay` + `module/aftersale` | 支付回调幂等、事务外调用第三方、退款失败重试 |
| 7 | `module/chat` + `config/WebSocketConfig` + `infra/RealtimePusher` | WebSocket（STOMP）实时推送 |
| 8 | `module/admin` | RBAC 权限、操作日志切面、数据看板汇总 |

每读完一个模块，就去 `backend/src/test` 找它的单测看一遍，单测是最直接的用法示例。

## 5. 关键流程的代码路线

### 5.1 担保交易：下单 → 支付 → 交货 → 确认收货放款

1. **下单**：`OrderController` → `OrderService.create`
   - Redis 记下 `requestId`，重复提交直接返回同一订单（幂等）。
   - `StockCache.tryDeduct` 在 Redis 预扣库存，不够直接拒绝；再用 `goods.version` 乐观锁扣数据库库存。
   - `OrderFlow.created`：写 `order_log`、通知卖家、在会话里插入系统消息，并通过 `DelayPublisher.schedule` 投递「15 分钟未支付自动取消」的延时消息。
2. **支付**：`OrderController` → `PaymentService.startPay` 返回收银台地址。支付宝回调 `PayCallbackController.notify` → `PaymentService.handlePaid`：按 `out_trade_no` 加状态条件更新，重复回调只处理一次，然后 `OrderFlow.transit` 把订单改成 40（待交货）。
3. **交货**：卖家调 `OrderService.deliver`，订单变成 50（待收货），同时投递「7 天自动确认收货」的延时消息。
4. **确认收货**：`OrderService.confirmReceipt` → `OrderFlow.finish` → `releaseToSeller` 放款。`balance_log (order_id, type)` 的唯一键保证同一订单只放款一次。

所有状态变化都经过 `OrderFlow.transit`：先用 `OrderStateMachine` 校验「当前状态 + 动作 + 操作人」，再带状态和版本号条件更新，最后写日志、发通知。

### 5.2 超时：延时队列 + 兜底扫描

- **主路径**：`DelayPublisher` 把消息发到带 TTL 的队列，到期后死信转到 `ct.timeout.q`（见 `infra/mq/RabbitConfig`）。`TimeoutListener.onTimeout` → `TimeoutService.handle` 会重新校验状态和截止时间，过时或重复的消息直接忽略。
- **兜底**：`OrderTimeoutJob` 每分钟扫一次数据库，补处理消息丢失或 MQ 宕机时漏掉的订单和售后。

这是「消息 + 对账」的常见组合：消息负责及时，扫描负责不漏。

### 5.3 售后与纠纷

`AfterSaleService.apply`（订单进入 60）→ 卖家 `agree` 或 `reject` → 被拒后买家 `appeal` → 管理员在 `admin/trade/AdminTradeController.arbitrate` 裁决 → `AfterSaleService.arbitrate`。

退款时先在事务外调用渠道退款（`PaymentService.refund`），成功后才在事务里改状态；失败就保持原状态，由 `OrderTimeoutJob` 定时重试。这样不会出现「库里显示已退款、钱却没退」的情况。

### 5.4 实时聊天

前端经 `/ws` 建立 STOMP 连接，`security/StompAuthInterceptor` 在 CONNECT 帧校验 JWT。发消息走 `ChatWsController.send` → `ChatService.send`：先落库，事务提交后再由 `RealtimePusher.push` 推到双方的 `/user/queue/messages`。WebSocket 不可用时，前端改用 `POST /conversations/{id}/messages`，走的是同一个 `ChatService.send`。

## 6. 中间件：用在哪、为什么用

| 中间件 | 用在哪 | 为什么 | 不可用时 |
| --- | --- | --- | --- |
| MySQL | 所有业务数据 | 事务、唯一键、乐观锁保证一致性 | 服务不可用 |
| Redis | token 黑名单（`TokenStore`）、限流（`RateLimiter`）、下单幂等、库存预扣（`StockCache`）、验证码、热搜（`HotWordService`）、在线状态（`OnlineTracker`）、敏感词多实例同步（`SensitiveWordSync`，发布订阅）、ES 同步游标 | 需要过期时间、原子操作或多实例共享的轻量状态 | 登录、下单等依赖它的功能失败 |
| RabbitMQ | 订单和售后的各类超时（TTL + 死信） | 到点精确触发，不用高频扫表 | 由 `OrderTimeoutJob` 每分钟兜底，超时处理最多晚一分钟 |
| Elasticsearch（可选） | 带关键词的商品搜索（`module/goods/search`） | 中文分词和相关度排序 | 默认不启用；启用后出错自动退回 MySQL 搜索 |

学中间件时，建议对照上表去读对应的类：每一处都写明了为什么用它，以及失败了怎么办。

## 7. 前端结构

```text
frontend/
├── index.html / admin.html     两个入口：用户端和后台
├── mock/                       内存版后端（npm run dev 时启用），按接口文档实现
└── src/
    ├── shared/                 两端共用：request.ts（axios 封装、统一错误处理）、类型、枚举、格式化、通用组件
    ├── web/                    用户端
    │   ├── api.ts              所有接口调用集中在这里，和接口文档章节一一对应
    │   ├── router.ts / views/  页面，大体和 prototype/*.html 对应
    │   ├── stores/             Pinia：登录态、未读数、AI 助手
    │   ├── realtime.ts         STOMP 连接与订阅
    │   └── assistant/          AI 助手浮窗
    └── admin/                  后台：api.ts、views/、stores/，结构同上
```

读前端时，从某个页面的 `views/*.vue` 出发，跟到 `api.ts`，再对照接口文档和后端 Controller，就能把一个功能从界面一直追到数据库。

## 8. AI 服务

`ai-service/app/`：`main.py` 是 FastAPI 入口，`graph/` 是 LangGraph 的对话图和工具（找物、规则问答、查订单、生成发布草稿），`rag/` 负责向量化和检索，`java_client.py` 带着用户 token 调用 Java 后端。它只读 MySQL，所有写操作都经过 Java 后端的接口和权限校验。详见 [ai-service/README.md](../ai-service/README.md)。
